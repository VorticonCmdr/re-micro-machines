# PLAN-ENGINE.md — M3: porting the game itself (race engine, drones, front end)

This expands `PLAN.md` §7 M3 ("engine port") into an executable sequence. It inherits every rule in `PLAN.md` and `CLAUDE.md`; the evidence it rests on is `docs/engine.md` (the 2026-09-20 disassembly pass: car record, physics step, state machine, terrain dispatch, drone AI, input, tournament rules — all `[STATIC]`, adversarially re-derived, corrections to the older docs listed in its §9).

## 1. Context

Every shipped asset is decoded and viewable (`PLAN.md` §6); the static world renders pixel-exact against a live frame (`npm run live`); the OPL2 driver model reproduces every register write the game caused (`npm run si2`). `index.html` is a placeholder. The remaining work is the game: the 35 Hz race loop with its physics, the drone AI, the car state machine, the race view with HUD, the sound events, and the menu/tournament front end.

What changed the shape of this plan:

- **The physics is deterministic.** `AdvancePseudoRandom48` has exactly two callers, both in the sound layer. Given the four per-step control bytes, the simulation is a pure function of the round files — so a per-step DOSBox trace can be matched *exactly*, not statistically. This is the oracle graphics and sound already have and physics did not.
- **The race is reachable under automation after all.** `UNKNOWN_race_live_reverify` blamed an attract-loop idle timeout and P2 = KEYS 1; the timeout is in the two-item menu helper (`FUN_0382`, 28.6 s) and KEYS 1 is J/L/I/M/K. The trace instrument is a milestone to schedule, not a wall.
- **The older docs were wrong in ~20 tagged places** (`docs/engine.md` §9) — the "projectile-hit routine" is the per-car integrate/commit routine, `[12ED]` is laps not checkpoints, state 1 is the hazard death not the start, the `37fc` carry check is live, the `'1 Up!'`/`'Failed'` handlers are swapped, sfx 1/2 are mislabelled. `PLAN.md` §8's own pitfall ("don't build on a citation you haven't re-disassembled") applies at scale, so **correcting the record was M3.0(b)** (`docs/engine.md` §9b) — done and verified in place (2026-09-24 documentation-debt pass, `PLAN.md` §7's own M3.0 note), well before the M3.x engine work that has since built on it.

## 4. The instrument: a per-step DOSBox trace

**What is captured.** At the per-physics-step breakpoint `1000:30B7` (first instruction after the per-car loop; map to the live segment with `debug_map_to_live`), read `DS:124A` for **0x590** bytes (the four car records) plus the globals `28F7` (tick), `2646–2650` (camera), `2652/2654`, `2670–267E` (scores/order), `26B4/26B8/26C4/26C6` (two-car lights, race over), `28BF/28C0/28C1`, `2911/2913`, `262F`. One row per step → `tools/refs/trace-R21-<name>.tsv`, columns named after `docs/engine.md` §1.

**Two-stage decomposition.** The records contain each car's `[137B]` control byte for that step, so:
1. *Physics given controls*: replay the trace's own four control bytes per step into `step.js` → positions, velocities, headings, speeds, states, progress, laps must match every step. Tests everything except the AI.
2. *AI given state*: run `ai.js` on the trace's state at step n → its output must equal the trace's drone control bytes at step n+1 (`PollAllCarInputs` runs before the step). Tests the drone logic in isolation.
Then the full loop (AI + physics) must reproduce the trace with only the human bytes fed in.

**Capture recipe** (`docs/engine.md` §6/§7; to be proven live and then written to `docs/boot-and-runtime.md`): boot per `docs/boot-and-runtime.md` → GAME OPTIONS → Enter release → title (no timeout) → `S` (P1 = KEYS 2 → fire) → main menu (28.6 s idle budget) → ONE PLAYER → RIGHT, `S` (Challenge) → character select `S` → PRESS ANY KEY → intro screen any key → `ROUND21` starts in state 0xA. Arm the breakpoint before the last key (pause → add → continue). First trace: **no human input at all** (car 0 idles in the grid, three drones race) — every subsystem except human steering is exercised and nothing depends on input timing. Second trace: a human-driven lap, with the control bytes coming from the records themselves. Alignment: the trace starts at the first step (state 0xA hold), so there is no offset to fit.

**Known risks and the fallback.** Per-step breakpoints are slow (~600 steps ≈ minutes) but unbounded; the Lua path is capped at 5 s / 1 M instructions / 64 KB output per run (`UNKNOWN_lua_hook_model`) and would need chunking. Replay determinism across sessions is `UNKNOWN_replay_determinism` — irrelevant to stage 1/2 above (the trace carries its own inputs), relevant only to human-tape replays. If breakpoint sampling proves unusable, fall back to `mem_snapshot` A/B at a `freeze`-pinned frame: pause at step n, dump, single-step one physics iteration (`debug_run_to 30B7`), dump again — one exact step diff per pair, which is still an exact oracle.

**`UNKNOWN_lua_hook_model` resolved 2026-09-20 (docs/engine.md §9f): the Lua path is what M3.4 actually used**, not the fallback — per-step breakpoints proved too slow round-trip-per-step for this session's tooling, while `dosbox.wait_frames(1)` + `dosbox.mem_read` per rendered frame worked directly. At the field width captured (a subset of `CarRecord`, not the full 0x164 B), the **64 KB output cap** binds first, at ~100 steps; the 5 s wall-clock cap was never reached. Reaching ≥ 600 steps this way needs chunking across multiple script runs (not yet done), not a different mechanism.

## 8. Pitfalls learned in this pass (for `PLAN.md` §8)

- **A NOP slide is not a dead function.** `37fc` (255 × `0x90`) *falls through* into `38fb`; the "dead" carry check is the race-load success test. Check what follows a NOP run before calling its caller's flag test dead.
- **Ghidra's listing is stale inside no-function gaps, and `disassemble_bytes … dry_run` returns the stale listing.** `5461`, `60fe–610b`, `643e`, `657e`, `662f`, `6abb`, `704a`, `885e` decode garbage; use `read_memory` and hand-decode, or create the function and re-disassemble.
- **Functions named after their sfx call site are not described by their name.** `FUN_1000_5be7` was "the projectile-hit routine" for a whole doc because it *contains* a sfx-1 site; it is the per-car integrate/commit routine. Read a function for its arithmetic before naming it.
- **`search_instructions` needs the operand without the closing bracket** to catch `MOV DI,0x1083`-style immediates; `'0x1083]'` found only the CALL and produced a false "installer unknown".
- **"Only writer" claims need a byte-pattern search, not an xref count.** `[28BF]` has four writers, `[26B8]` six; get_xrefs_to misses every DS-relative one.
- **A table's stride and count must be read from the indexing code, not from the file's field size.** `DecayBounce` is a *word* table indexed by `round·2` (the doc said 10 words by round — right by luck); the state-2/D animation has 6 *steps* but 5 *frames*.
- **The verifier's refutations were the highest-value output of the fan-out** (bounce formula, lap rule, static image, `[2656]` meaning, the 0x594 over-read). Keep the adversarial pass; budget for it.
- **A second, independent derivation of the same formula WILL drift once the first one is fixed and the second isn't.** `check-trace.mjs`'s own `staticFieldsFor` duplicated `spawnCars`'s per-car tuning computation instead of calling it; M3.20 fixed the real `CX` handicap in `spawnCars` and nobody thought to check the duplicate, so a real bug (`UNKNOWN_kidmodifier_use`) stayed fixed in one place while its own trace-oracle test kept "confirming" the pre-fix behavior for two more milestones (M3.22, docs/engine.md §9aa). Extract a shared function instead of copying a formula a second time, even into test/tool code.
- **A long-running DOSBox instance accumulates stale menu/input state that looks like a tooling bug.** A managed instance left running across sessions can land on the wrong menu default and stop accepting input entirely on a specific screen; `dosbox_shutdown`+`bridge_start` for a clean boot is faster than diagnosing it (M3.22).
- **Two independent mistakes that happen to agree are harder to catch than one, because the cross-check that would normally catch either one passes.** M3.22's own live cross-check read as "28 of 28 tuning fields match" — actually 25 of 28, with the 3 misses (`maxSpeedBase` × 3 drones) hidden because a transcription error (writing the wrong live-read value) and a pre-existing formula bug (`tuningFieldsFor`'s `maxSpeedBase: info[0]`) both independently said "1662," so they matched each other instead of catching each other (M3.23, docs/engine.md §9aa's own correction note, §9ab). Neither error alone would have survived the check; both together sailed through. When a value comes from re-deriving a formula AND a live read, cross-checking the two doesn't prove either is right if you never independently re-verify the raw capture itself.
- **When a fix reverts because it broke a real test, document the fix attempt and the reason it failed — don't just silently discard it and move on.** M3.23's attempt to gate `updateCarTileCollision` on `active`/`state` (matching the real bytes exactly) broke round 3's drop-in sequencer test, because `bounceAndCommit`'s own commit gate (state 0/2/0xE) doesn't line up with the collision function's own gate (state 0 only) the way a naive port-side mirror assumes. The revert plus a precise note on WHY (`bounceAndCommit` needs to read persistent fields, not this call's own ephemeral `hit`, before the gate is safe to add) is worth more to whoever picks this up next than either shipping the regression or silently reverting with no trace of what was tried.
- **A whole-record gate built to avoid a crash can discard real data along with the missing data it was actually guarding against.** `dirTile()`'s bare `.subarray()` would return a short (not `undefined`-safe) array for a file that ends mid-tile, so `collide.js` gated on the WHOLE tile index being in range — which also threw away round 5's own real 18-of-36 bytes for meta-tile 56, not just the genuinely-missing 18 (M3.24, docs/engine.md §9ac). The fix wasn't to widen the gate's threshold, it was to make the primitive itself safe per-byte (zero-fill only what's actually missing) so the caller never needed a whole-record gate at all. When a bounds check exists to prevent a crash, check whether it's also silently discarding partial-but-real data the crash-prevention didn't actually require losing.
- **Before assuming an out-of-range value is unreachable OR guessing what a real "undefined" fallback would be, check both — a flood fill answers reachability directly, and a real load-order trace can pin down "undefined" precisely instead of leaving it as a shrug.** M3.24 settled `UNKNOWN_tile_index_overflow`'s three cases with two different techniques suited to two different questions: a full sub-cell flood fill from each race's own start position (not eyeballing map coordinates) proved two cases structurally unreachable outright; for the one reachable case, simulating the real game's own fixed `ORDER_TABLE` load sequence pinned the exact real stale byte to a specific round's own real data, not a hand-wave. Neither required a live DOSBox session — both were answerable from the shipped files and the disassembled load routine alone.
- **A confirmed-dead pattern in one place doesn't mean every structurally-similar case is also dead — check each one, don't extrapolate the verdict.** `UNKNOWN_tile_index_overflow`'s own round 8/9 cases (`.COL`/`.DIR`) were confirmed unreachable; `.BRK`'s own sibling case (round 3, M3.25, docs/engine.md §9ad) shares the exact same fixed-buffer-never-cleared mechanism but turned out to be the OPPOSITE verdict — genuinely reachable, real course data, not a dead corner. Both conclusions came from running the SAME flood-fill technique fresh on the new case, not from assuming the first case's own "unreachable" verdict would generalize. A shared mechanism is a reason to check a sibling case with the same rigor, not a reason to skip checking it.
- **A doc's own "Open items" section and its inline section body can silently disagree after only one of them gets updated — check both before citing either as current.** `docs/track-layout.md`'s "Open items" list had `UNKNOWN_589c_progress_transform` marked resolved; the `.MAP` section's own inline paragraph, a few hundred lines earlier in the SAME file, still said "not fully unwound." Re-disassembling settled which one was stale (the inline note), but the fix that actually mattered was reading both and noticing they disagreed, not trusting whichever was read first. **The same failure mode recurs ACROSS sibling docs, not just within one file**: `UNKNOWN_ct_tile_pixel_layout` was fully resolved in `docs/track-graphics.md` (the `.CT` byte layout, correctly implemented in `src/formats/race.js` since the M3.2 era) but `docs/track-layout.md`'s own `.CT` section still posed it as open, because whoever wrote the resolution in one doc never went back to close the citation in the other (2026-09-23). Before trusting an `UNKNOWN_*` item is genuinely still open, grep for its name across ALL docs, not just the one file it's cited in — a parallel research fan-out (port code, fresh disassembly, and the existing render-oracle's actual scope) settled this one in minutes once framed as "check whether this is already answered somewhere," not "investigate this from scratch."
- **Gating half a real function while a second port-side function stands in for the other half breaks the moment the gate is added — trace the actual regression instead of assuming the fix must be wrong.** M3.26's naive `active`/`state==0` gate on `updateCarTileCollision` broke the round 3 drop-in test a SECOND way, distinct from M3.23's own reverted attempt: the real `UpdateCarTileCollisionSfx6or4` also computes `nextX`/`nextY` under that same gate, but this port's `integrateCar` is a separate, always-unconditional function standing in for that half — so gating one without the other silently changes when position integration happens relative to state. The fix wasn't to revert again; it was to trace the actual velocity/slide interaction tick-by-tick (a five-line instrumented script, not more disassembly first) and discover the OLD, unconditional behavior had itself been measuring a bug (spurious wall bounces mid-slide) that the test's own hardcoded tick-count baseline had quietly enshrined as "correct." When a gate you're confident matches the real bytes breaks a passing test, isolate which specific change is responsible (temporarily disable just the gate, keep the rest) before concluding the gate itself is wrong — it may be the TEST's own baseline that was never right.
- **When a ported function's own name encodes an effect, check whether the port actually performs that effect.** M3.27 found two real, previously-unwired sound gaps this way: `terrain.js`'s `h61b0` was already named `HandleTerrainRoughSurfaceSfx6` and `h669b` was already named `HandleTileLowGripSfx12` — both had their real physics ported exactly, and NEITHER called `playSfx()` at all. The function's own name had been advertising the missing behavior since whichever earlier pass first read the disassembly and chose that name, and nobody had checked the port's own body against its own label since. This generalizes past sound: any time a Ghidra-derived function name (or an inline comment quoting one) names a side effect, that's a free, specific hypothesis to check against the ported body, not just documentation to trust.
- **A whole 224-instruction function is worth fully re-disassembling even when only a small slice of it is the actual target — a partially-read function can hide an entire second branch with its own separate effect.** M3.27 re-disassembled `UpdateCarAirborneLandingSfx` in full while chasing one missing sfx site and found the ALREADY-PORTED "Path A" (primary landing) was only half the function: "Path B" (a decay-bounce arc restarting) fires the identical sfx dispatch every time it runs and had never been read at all, since the port's own "Lift-off" branch had only ever been read for its physics. The same full re-read also surfaced a missing `knockoutX`/`knockoutY` recording on ramp-jump landings (the same class of bug M3.23 found in a different function) — a second, unrelated finding that fell out of reading the whole function rather than just the part the task nominally asked about.
- **Re-verifying an old `[STATIC]` claim while closing an `UNKNOWN_*` can invalidate the very premise the item was framed around, not just answer the question as posed.** `UNKNOWN_brk_nibble_reuse` was framed as "why does the data distinguish 0/4/15 when the one consumer treats them identically" — a full re-disassembly of `RunDroneSteeringAi` (M3.29) found that framing itself was wrong: nibble `0` takes an earlier, direct jump that bypasses the branch `3`/`4`/`15` share, so `0` and `4`/`15` were never actually identical, only `3`/`4`/`15` are. Closing an old citation is a live re-derivation, not a lookup — read the cited disassembly range again in full rather than trusting a prior session's own characterization of what it found there.
- **When timing a live event through a remote debugger bridge, the tool-call round-trip itself can exceed the event being measured — use the emulator's own clock, not wall-clock polling across calls.** M3.30's first attempt at timing `SM.EXE`'s logo intro polled `screen_info` between typed commands and measured a wildly inflated ~15-30s, because each poll itself took several seconds of real time and routinely overshot straight past the actual ~4.7s event. The fix wasn't tighter polling — it was reading the emulator's OWN clock (the BIOS tick counter, `0040:006C`) at the exact moment a memory-write breakpoint froze the CPU on the signal that mattered (the BIOS video-mode byte, `0040:0049`, written by every `INT 10h` mode change regardless of which program makes it): since the CPU is genuinely paused while the breakpoint holds, the tick value read afterward is exact regardless of how long the read itself takes. Any time a live measurement's own answer is `1000+` calls, or needs sub-second precision the polling interval can't offer, reach for a breakpoint-plus-emulator-clock reading instead of an external stopwatch.
- **A single early-exit gate in the disassembly can span more phenomena than a prior citation named, so "unconditional" needs to be re-checked against the actual jump targets, not carried forward from a description of a DIFFERENT part of the same function.** §9ae described the hit-flag clear at `5d1d-5d32` as "runs every call regardless of whether the bounce fired" while deriving something else (the LEV/progress commit fix); re-disassembling the SAME range fresh for M3.31 found both outer gates (`5c75`/`5c7f`) `JMP` past `5d1d` entirely when either check fails, so the clear is scoped to the identical `wallHitPending && wallBounceEnable` condition as the bounce mutation right next to it — a second, real, previously-unported gate the first pass's own true-for-its-own-purpose framing had obscured. When advisor guidance says "re-derive, don't trust the prior citation," treat that literally for the WHOLE addressed range, not just the specific instructions the citation was actually about.
- **"The real code doesn't bother correcting this case, so it can't matter" needs a worked counter-example, not just a plausibility argument.** M3.32's own investigating agent argued the real car-draw functions' one-sided wraparound correction (only ever corrects a camera-relative delta that's gone very negative, never one that's gone very positive) was "provably benign to skip" versus this port's general symmetric `wrapDelta`, reasoning any delta needing correction was already off-screen either way. A worked example (a car placed just across the world's toroidal coordinate seam from the camera) showed this backwards: the real code's missing positive-side correction means the ORIGINAL game fails to draw that car at all in this scenario, while this port's symmetric wrap draws it anyway — a genuine, if narrow, divergence the plausibility argument never actually tested. When a "this can't matter" claim about skipped real-code behavior doesn't cite a concrete input that would expose the difference, construct one before accepting it.
