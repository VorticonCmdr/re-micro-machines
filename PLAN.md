# PLAN.md — porting Micro Machines (DOS, 1994) to HTML + vanilla JS

This is the working plan. It carries the constraints, the architecture, the reverse-engineering method, the per-format status, the milestone order and a pitfalls list where every entry is a real wrong answer that was caught. Read it before writing any decoder. Evidence tags (`[PROVEN]` / `[STATIC]` / `[UNKNOWN]`) are defined in `CLAUDE.md`; per-subsystem findings live in `docs/`.

## 1. Goal and non-negotiables

- **Port the game to the browser** as plain HTML + vanilla JS modules, built with Vite. No framework, no TypeScript, no asset pipeline.
- **Assets are loaded from the original files at runtime, unmodified.** No extraction step, no converted copies, nothing generated at build time. Decoders take the bytes of `game/…` exactly as shipped (`fetch().arrayBuffer()` in dev; the user's own folder via the File System Access API when built). The production build must never contain game data (`publicDir: false`; `game/` is git-ignored).
- **Ghidra disassembly is ground truth.** The decompiler is for orientation only: this is 16-bit real-mode code with segment tricks and loadable code modules, and decompiled output has been explicitly ruled out as evidence. Every structural claim in `docs/` cites a `1000:`-based Ghidra address in `MICROU.EXE` (or `SM.EXE`), a file offset with the byte check that was run, or a live DOSBox observation.
- **Render and look.** A decoder is verified when its output has been rendered to a PNG (or played) and looked at, and — where possible — compared with what DOSBox shows or holds in memory. Parsing without throwing proves nothing.
- **First deliverable: `viewer.html`**, an asset viewer that can show or play every shipped asset. The game page (`index.html`) comes after the formats are known.

## 3. Architecture (mirrors `../duke`, the finished sibling port)

```
game/                original files (read-only, git-ignored); game/GAME1/ is the one shipped "game set"
viewer.html          dev asset viewer            index.html   the game (later)
src/io/source.js     FetchSource | DirectorySource | DropSource — one read(path) interface; paths are relative
                     to game/ ('GAME1/ROUND1.PAL'); DOS-case-insensitive keys
src/data/catalog.js  hand-maintained inventory: path, family, view kind, decoder status, notes
src/formats/*.js     pure, DOM-free decoders (bytes → typed structures / indexed pixels). Node imports them too.
src/render/raster.js indexed → RGBA → canvas at integer zoom (4:3 only at zoom % 5 == 0)
src/ui/              app shell, dom helpers, one view module per catalogue kind
tools/*.mjs          render-and-look verification: same decoders, PNG out, run under Node
docs/*.md            findings by subsystem, every claim tagged and cited
```

Rules of the codebase:
- A decoder module exports functions that take `Uint8Array` and return plain data; no DOM, no fetch. Views do the fetching and drawing.
- `catalog.js` is the only place that knows which file is what; a new decoder means a new `KIND`, a view, a `VIEWS` line in `src/ui/app.js`, and a status upgrade in the catalogue.
- `MICROU.EXE` runs with `GAME1/` as its working directory (it opens `..\BITSFILE.PH0`), so anything the engine port does with paths must keep that model: a "game set" directory plus the shared files one level up.
- 6-bit DAC palettes are expanded with `round(v·255/63)` (`dac6ToRgb8` in `src/formats/pal.js`) — that is what makes the DOSBox pixel diff exact; bit replication left 67 mismatches, `v*4` tens of thousands.

## 4. Reverse-engineering method

1. **Start from the consumer, not the bytes.** For every file: find the `INT 21h AH=3Dh/3Fh` site that loads it, follow the buffer to the code that indexes it, and read the address arithmetic. Byte-pattern guessing on `.MAP` produced a refuted hypothesis on day one (see Pitfalls) — the disassembly settles in minutes what statistics can only hint at.
2. **Cite the instruction.** Loop bounds, strides, field offsets and pixel order come from specific instructions at specific addresses. Record them in the doc and as Ghidra comments/labels (PascalCase names) so the next session does not redo the work.
3. **Live oracle.** The DOSBox bridge can break on any `INT 21h`, dump any buffer (`mem_read`), read the DAC and the `A000:0000` frame buffer, and screenshot. The strongest verification of a decoder is a byte-for-byte comparison of its output against the game's own decoded buffer in memory, or a pixel diff against a captured frame. There is exactly one emulator instance — one driver at a time.
4. **Tag honestly.** `[STATIC]` from disassembly/bytes, `[PROVEN]` only after a live or rendered check, `UNKNOWN_<id>` for everything else. Record refutations so they are not re-derived.
5. **Adversarial review.** Findings from a fan-out are reviewed by three lenses (re-read the disassembly; re-run the byte check on every file of the type; construct a competing interpretation) before they are built on. Contested claims stay out of decoders until settled live.

## 5. Verification strategy for decoders

- `npm run render` writes PNGs for every decoded family from the same modules the browser uses. Look at them after every decoder change.
- For graphics: compare against a DOSBox `screen_capture` of the same content, or against a memory dump of the decoded asset taken with the bridge; count differing pixels rather than eyeballing when the question is "is this exactly the game".
- For layouts (tracks): render the track from `.MAP` + tiles and compare with a live race frame; overlay start positions from `STRT_POS.BIN`.
- For sound: the Sound Images driver's output is the reference — the OPL register stream captured under DOSBox is diffed against the JS model's stream (`npm run si2`, exact); audio-level comparison of the OPL2 core against a reference emulator is still open.
- The catalogue must always match the directory (`npm run catalog`), and every view must survive the headless smoke test (`npm run smoke`) — it caught nothing yet but it is the only thing that exercises the views without a browser.

## 8. Pitfalls (each one was a real wrong answer)

- **`file(1)` calls `MICRO.EXE` a "PKZIP self-extractor".** It is PKLITE-packed (banner at 0x1C). `MICROU.EXE` is the unpacked form and the only sensible disassembly target.
- **Ghidra's MZ import stops after 7 instructions.** The header entry is a PKLITE stub that `RETF`s to `<load seg>:0006`. Create a function at `1000:0006` and re-analyse (1 → 169 functions).
- **`.MAP` is not a 32×32 grid of 16-bit indices into `.COL`.** Values reach 0xFFFF and over half exceed the table size; neither byte lane looks like a flag byte. Tested on all 29 files. Start from the consumer code instead.
- **Vite's SPA fallback answers `200 text/html` for missing files.** `FetchSource` must reject HTML bodies or every missing file looks present.
- **`curl … | cmp -` reported a false mismatch on `MICROU.EXE`.** Save to a file and `cmp` that; every served file is byte-identical.
- **A Ghidra instance may have a different sibling project open.** Check `list_instances` before trusting any `mcp__ghidra__*` result; always pass the program name.
- **Interrupt breakpoints in the DOSBox bridge do nothing until armed** by a pause → add → continue cycle; `debug_breakpoint_list` shows `active`.
- **`SM.EXE` is not the copy protection and `FONT.BIN` is not a font.** Watching the screens said "SM.EXE shows the code card"; the disassembly says `SM.EXE` is the logo intro and `FONT.BIN` (loaded by `MICRO.EXE`) draws the card. Name things from the code, not from what appears when.
- **`.CHR` descriptor dimensions are (height, width).** Reading them as (width, height) sheared `MINATURE.CHR` and `LOGO.CHR` into stripes; the file-I/O agent's first render "did not look sensible" for exactly this reason.
- **A series template's digit is the LAST character.** `loadSeries` first used a regex that never matched, so it re-read `PR0` forever and the render tool hung for three minutes. Patch the last character, as `1000:3564` does, and cap the loop.
- **The OPL register stream is only as reproducible as the driver's *pending* pipeline.** Modelling `AH=4` as "start the tune" matched 50 writes; modelling the driver's pending flags, the `JCXZ` skip in `DoPendingStopMusic`, the file-seeded accumulators/division and the tick gate got 1500/1500. The game issues stop/reset/start in one frame and relies on the next-tick semantics.
- **A driver's variables ship with non-zero values.** `DRIVER1.BIN`'s accumulators (`+0x1265`) and division/tempo (`+0x125E` = 192/120, not a tune's 96/120) are live state saved into the file; a model that zero-initialises them drifts by a tick.
- **"The driver got no tick during its load" was a fact about one session, not a rule.** The first live capture had one timer tick gated off inside the driver load; a second session had none, and each capture is bit-exact only under its own count. The rule that fits both is relative to the game, not the load: the first driver tick is the one after the game's first post-load command. Verify timing rules on two sessions before hard-coding them.
- **A queue is not an array.** The sfx queue was modelled as a JS array with `push`/`shift`; the driver's is 8 bytes with first-zero insert, engine-id dedupe and priority replacement, and the drain order decides which OPL channel a sound gets. Five engine updates then piled five looping slots onto one car in the viewer while the game keeps one (`AH=0A` before every `AH=5`). Replay tests that only feed the game's own command log cannot catch a wrapper that issues commands the game never would — test the wrapper's idiom separately (`npm run si2`).
- **A live-verification session can end up unable to reach the state it needs.** Menu automation through the bridge lost every key press to the title attract loop's idle timeout, and this copy's `SETTINGS.DAT` (P2 = KEYS 1) made the one reachable branch a dead end; the race half of the sound claims stayed single-capture. Write the navigation recipe (`docs/sound.md` §8) into the docs when it is found, and budget for it.
- **Exclusion boxes for a live diff must be measured, not eyeballed.** The boat in the reference frame is at view (118..136, 88..111); a box guessed from a downscaled picture put it 100 px away and reported a false regression.
- **Ghidra's `search_strings`/`list_strings` can silently miss a real string.** `"TANKS"` is a plain NUL-terminated string at `193C:0074`, plainly visible with `strings -a` and a raw memory read, but the auto-analyzer never classified it as a String data item — every string-search call came back empty for it. A vehicle-class table re-derived only through Ghidra's string tools would land one class short from TANKS onward and look internally consistent while being wrong. Cross-check a string-table read against a raw byte dump, not just the string-search tools.
- **The smoke test's dedup key hid three view branches from itself.** `check-views.mjs` deduped on `kind + round`, but `.COL`/`.DIR`/`.CT` (and `.LEV`/`.BRK`) share one catalogue `KIND` per family; whichever file catalog.js pushes first for a round (always `.COL`, then `.LEV`) won every time, so `104/104` and `78/0` "passing" smoke runs had never once called the view code for `.DIR`, `.CT` or `.BRK`. Found only because the newly-added `.DIR` render needed checking and a direct count showed 0 representative entries for it. Fixed by folding the file extension into the dedup key (125 representative entries). That fix immediately created the SAME bug one level down: `STRT_POS.BIN` and `CHEATS.BIN` both have no round number and both end in `.BIN`, so the extension-based key collapsed them into each other too — one silently untested again. Final fix: only dedup files whose name actually contains a round number; everything else (global, one-off files) gets its own path as the key and is never deduped. A test that silently skips whole branches and still prints "0 failed" is worse than no test — check what a dedup key actually collapses before trusting its pass count, and re-check after every change to the key, not just once.
- **`disassemble_bytes` from an unverified address decodes garbage that looks like a real instruction.** Starting a read at `1000:5461` (chosen because an earlier call's output happened to end there) decoded `SBB BX,[BX+DI]` — a real, plausible-looking x86 instruction — because `5461` is two bytes into an actual 4-byte `ADD SI,0x191B` that starts at `545F`; the disassembler has no way to know it landed mid-instruction and just resyncs from the wrong byte. Caught only because `read_memory` on the same range gave different bytes when hand-decoded. Only start `disassemble_bytes` from a verified boundary — a function entry, or the byte right after a `CALL`/`RET`/unconditional `JMP` — never from an offset picked because a previous tool call's output happened to stop there; cross-check with `read_memory` if a decode looks locally sensible but doesn't fit the surrounding logic.
- **A documented function name and address can be flat wrong, not just incomplete.** `docs/track-layout.md` cited `SetupRaceLoadAllRoundFiles 1000:37fc` with a specific file-load order for over a session's worth of work; the address is 255 bytes of `0x90` padding in the actual file (confirmed both in Ghidra and in the raw EXE bytes), not a function at all — the load order built on it was never traced, only asserted. Found by disassembling the address directly instead of trusting the existing doc/name; renamed in Ghidra to `NoppedOut255bStub` with the raw-byte evidence in its plate comment. Don't build on a citation you haven't independently re-disassembled, even one already in `docs/`.
- **A verification tool with a real bug can look "done" for months because it never had output to check.** `tools/render-tunes.mjs`'s sfx path called `setup(seq)` before the sequencer's first `hostTick()`; the reset that same tick wiped the just-queued sfx id before it started, so every sfx render was silent (0 audible writes) — invisible until an agent actually inspected the render pipeline's numbers instead of trusting that "it ran without throwing" meant it worked. Tick the pending reset through before queuing anything new.
- **The game set lives one directory down.** Asset paths are `GAME1/…` and the engine's CWD is `GAME1/`; a flat filename map (as in `duke`) does not fit.
- **A `DX=0xHHLL` packed-dimension argument is ambiguous until you disassemble the callee's loop, not the caller.** Reasoning "`DX=0x1008`, and `DX=0x1010` elsewhere means 16×16, so `0x1008` must be 16×8" is invalid — `0x1010` is symmetric and proves nothing about byte order. `BITSFILE.PH0`'s digit table was recorded as 16×8 glyphs (and rendered as a plausible-looking but actually-garbled strip) until disassembling `BlitSpriteAtBufferOffset 1000:8D09` showed its inner per-row loop count comes from `DL` and its outer row-count from `DH` — the digits are 8×16, and re-rendering at the corrected geometry reads cleanly as "0123456789". A render that "looks roughly plausible" is not confirmation; a render that reads as unambiguous real content (text, digits, a recognizable icon) is.
- **A round gate on the *draw* call does not mean the *data* is only ever used in that round.** `BITSFILE.PH0+0x1F00` was documented as "a round-8 splash animation" solely because the one draw call site found first (`DrawRound8ExtraAnim32`) is gated on `[0x28BF]==8` — without checking whether the *other* caller of the same low-level blit (`FUN_1000_8386`, which has no round gate) is ever actually triggered outside round 8. It is: a separate, round-2-gated site (`1000:74A3`) sets the trigger flag that `FUN_1000_8386` consumes. The slot is genuinely dual-purpose — PH0's own bytes are a live round-2 boat-splash; `ROUND8BR.VH0`'s bytes get copied over the same slot only for round 8's chopper rotor — and calling PH0's own content "dead"/"inert" was an overcorrection in the other direction. When a draw call is gated one way, trace every *trigger* write for that call's precondition too, not just the draw site.
- **A NOP slide is not a dead function.** `1000:37fc` (255 × `0x90`) was documented as a routine whose returned carry flag "a NOP run touches no flags, so that check is effectively dead" — wrong: the NOP run *falls through* into real code (`LoadRaceStartPosCheatsMapAndBanks 1000:38fb`), and the "dead" check was in fact the live race-load success test. Check what follows a NOP run, not just what a NOP run itself does, before calling its caller's flag test dead (`docs/engine.md` §2/§9).
- **Ghidra's listing is stale inside no-function gaps, and `disassemble_bytes … dry_run` returns that stale listing, not a fresh decode.** In the engine pass, `5461`, `60fe–610b`, `643e`, `657e`, `662f`, `6abb`, `704a` and `885e` all decoded garbage inside unbounded regions (`5429–5531`, `60cb–6230`, `63d6–6673`, `66b2–683b`, `6882–73e6`, `880a–8995`) — a repeat of the `5461` pitfall above, at eight more addresses, because a `dry_run` disassembly re-reports the existing (wrong) listing instead of re-decoding the bytes. Use `read_memory` and hand-decode inside any gap, or create the function and re-run analysis, then re-check with `read_memory` — not with the post-analysis listing.
- **A function named after one of its call sites is not described by that name.** `FUN_1000_5be7` had been "the tank/projectile-hit routine" for a full session because it *contains* a sfx-1 call site reached from the tank projectile-hit path; reading the function's actual arithmetic shows it is the per-car integrate/wall-bounce/position-commit routine, called for all four cars every physics step — the projectile-hit test is one of several things it does near its exit, not what it is. A name assigned from a downstream side effect (a queued sound, a set flag) can be flatly wrong about the function's actual role; read the arithmetic before trusting or assigning a name.
- **`search_instructions` needs the bare operand, not `operand]`.** Searching `'0x1083]'` (with the closing bracket, matching how the field is normally written as `[BX+0x1083]`) found only the one `CALL [1083]` site and produced a false "the input-reader-table installer is unknown"; the actual installer (`MOV DI,0x1083`) uses the immediate without a bracket and was found only by searching `'0x1083'` bare. When a search comes back suspiciously empty, retry without the bracket before recording an `UNKNOWN`.
- **An "only writer" claim from `get_xrefs_to`/casual grep needs a byte-pattern search across the whole image, not an xref count.** `[DS:28BF]` (round number) was recorded as having "one writer"; a byte-pattern search over the *entire* 83662-byte image found four `MOV [28BF],AL` sites, all unpacking the same unrelated menu path's tournament-order byte identically. `[DS:26B8]` similarly had four writers recorded where six exist. DS-relative globals are exactly the case `get_xrefs_to` misses (`docs/ghidra-evidence` territory) — a claim of exclusivity needs `search_byte_patterns`/`search_instructions` over the whole file, not a tool that can silently under-count.
- **A reviewer's "correction" is a claim like any other — when it says two code blocks differ, diff the instructions.** `docs/engine.md` §3's first draft said the camera's X and Y axes were smoothed the same way; a review pass flagged that as papering over an asymmetry and the paragraph was rewritten to "X always applies a bounded step". The two blocks (`1000:5126-5152`, `5156-5186`) are the same instruction sequence with different operands — the rewrite had missed a `JMP` that skips the ±step block — and `camera.js` faithfully ported the wrong reading, so from M3.6 to M3.10 a settled camera overshot any target within 50px by up to 50px every physics step and swung back the next (`docs/engine.md` §9m). Neither the original author nor the reviewer had put the two disassemblies side by side.
- **A screenshot cannot show a per-frame oscillation, and a determinism test happily reproduces one.** The ±50px camera shake above sat behind 18 green checks and several "confirmed live" notes: every frame was individually valid, `check-play.mjs` only asserted finite/in-world/identical-across-runs, and an oscillating camera is all three. It was reported by the user as "flickering, but the screenshot looks normal". Anything that moves over time needs a *sequence* assertion (here: a settled camera sits exactly on its target every step; per-step move never exceeds the approach step), not a frame check — and the new check was run against the old code first to prove it actually fails.
- **A table's stride and entry count come from the code that indexes it, not from a plausible read of the file layout.** `DecayBounce` looked like "10 bytes, one per round" from its size; disassembling `UpdateCarAirborneLandingSfx 1000:7429` showed it is a **word** table indexed by `round·2`, and a naive byte-per-round read would silently pull the wrong half of every entry. Confirm a table's element width and stride from the `ADD/SHL/IMUL` that builds its index, every time, even when the file size "just works out."
- **`1000:` and the DS segment are different address spaces even though both are written as 4 hex digits, and Ghidra's `apply_data_type` will not warn you if you confuse them.** Applying the `CarRecord` struct (created for the car-record fields, which live at `DS:124A` = `193C:124A`) at `1000:124a` instead — the *code* segment's offset `124A`, which happens to fall inside a real function (`ShowNextRaceIntroScreenTune4or5`) — silently "succeeded" and overwrote part of that function's disassembly with garbage struct data; a sibling mistake at `1000:1512` did the same to `ShowRaceResultsScreenTune8or6`. Both were recoverable (the underlying bytes are untouched by `apply_data_type`; shrinking the wrong data down with `apply_data_type(..., "undefined1")` and then `disassemble_bytes` over the freed range restored the code), except for one stray single byte at each site that no available tool (`disassemble_bytes`, `clear_flow_and_repair` — which never clears Data — nor `run_script_inline`, disabled in this environment) could fully undefine; both are flagged with an EOL comment giving the correct bytes. **Always state which segment a `1000:` vs `DS:`/`193C:` address is before applying a data type**, and prefer a dry run that specifically checks for `type_would_evict` against *named* symbols — an eviction-of-named-globals rejection is exactly this class of mistake catching itself, and a *success* at a `1000:` address for what should be DS-relative data is a hazard sign, not a green light.

- **A raw absolute offset from a disassembly and a struct's own relative-offset field table are not directly comparable — convert before concluding a field is missing.** The mistake above, generalized: `car.js`'s `FIELDS` array is indexed relative to `CAR_RECORD_BASE` (`0x124A`), so `[BX+0x1278]` in a disassembly listing is field-table offset `0x1278-0x124A=0x2E`, not `0x1278`. - **A per-car control site that "isn't being reached" may just be gated on state, not on whatever condition the test is actually varying — check the state field directly before concluding anything from a missing hit.** A live rubber-band test (M3.42) forced several cars' fields and a breakpoint at the accel-apply site (`4E8E`) simply never fired, tick after tick, across every drone in the race — read as "the AI isn't requesting acceleration this tick." Read the state field directly the moment a conditionally-gated site stops firing, before spending more ticks hypothesizing about what condition might be suppressing it (`docs/engine.md` §9aq 1).
- **A live value that looks "well past" a formula's prediction may just be two real writers of the same field firing on the same tick, not a bug in either one — replay the port's own function on the exact live inputs before calling a value unexplained.** A live capture (§9aq 3) had a no-throttle control byte push a car's `speed` from 64 to 235, "well past" the ~44 a coastDecel-only reading of the decay rule predicts — flagged as a new, unexplained open item across two doc sections (M3.42). Before recording a live value as unexplained, run the port's own code on the same inputs — a working, checked-in decoder is a faster, more decisive check than reasoning about which disassembled function might explain a number.
- **A reachability sweep's own harness can silently double a step, or silently answer a different question than the one asked — check both before trusting a "zero disagreements" count.** Measuring how often M3.44's car-draw wrap fix actually changes a real frame, a first sweep manually called `updateCamera` after `runStep` — not knowing `runStep` already calls it internally via `ctx.camera` (`step.js:333`) — so the camera advanced twice per tick from the second step onward, silently halving its own lag behind the target and understating how close to the world seam it could ever get. - **A car-record field is unnamed only if the ABSOLUTE `[BX+n]` offset was grepped, not the relative one.** While tracing an alternate tuning path, `[BX+0x12A4]` was called "no name anywhere in this port" from a literal grep for `0x12a4` — but `car.js`'s field table stores offsets relative to `CAR_RECORD_BASE=0x124A`, so `0x12A4` is really `0x5A` there (`brakeDecel`, already ported and already matching the cited bytes exactly). Repeated for three more fields in the same session before being caught. Subtract the base before grepping, or grep the field-table file's own `offset:` lines instead of a raw hex literal.
- **The same memory cell can be addressed two different ways in the same binary, and a byte-pattern search for one encoding finds none of the other.** `CS:[0x9C62]` and `DS:[0x8A2]` are the identical physical byte (`CS`/`DS`'s own segment bases put both at linear `0x19C62`), but one region of code reaches it via a `CS:`-prefixed direct address (bytes `62 9C`) and another via a plain `DS`-relative one (bytes `A2 08`) — a search for only the first found 2 writers and called the gate "very likely always-satisfied," missing 3 more writers (including the one that actually matters) reached only by the second encoding. When a global's own writer set looks suspiciously thin, or a "write-only" conclusion feels too convenient, search every plausible encoding (segment-prefixed AND flat) before concluding a search was exhaustive.
- **A branch's own "unconditional" citation can be true for the ONE instruction checked and false for the whole block it was used to justify — trace the branch that was NOT taken too, all the way to where it rejoins (or doesn't).** `tuningFieldsFor`'s own car-index gate (`4070: CMP BX,0`) was correctly found unconditional on raceFormat, and that correctness was then, wrongly, generalized to the whole `3FBE-4134` region containing it — because the OTHER branch of an earlier fork (`3F30: CMP CS:[9C62],0`) was read only partway (stopped at a `NEG DX`, before seeing where the result landed) and assumed to fall through into the same shared path. Read a not-taken branch all the way to its OWN exit (a `RET`, or a jump target outside the block being justified) before calling anything upstream of a fork "unconditional."
- **A held key can silently satisfy the SAME exit test two different real screens share, closing the second one before it's ever visible — and the automation tool's own "hold" needs checking too.** Testing two-human H2H's handicap question (`0B51`) live, holding P1's fire key continuously through the character carousel's own ~1.1s commit animation and straight into whatever followed skipped the handicap screen entirely, with no visible trace it ever ran — `0B51`'s own poll loop (`0BEC`) tests the SAME fire bit the carousel's own commit used, with no release-wait at its own entry (unlike a documented sibling screen elsewhere in this codebase that DOES clear the release latch first), so an already-held key satisfies its exit test on the very first poll and it resolves instantly with whatever default was already stored (`docs/engine.md` §9bk). - **A conditional gate near a function's own END does not mean the function is a no-op when the gate fails — read from the entry to the gate, not just the gate.** `DrawH2HWinRecordDigits` (`1000:240A-2480`) was read, twice across two separate commits, as "jumps straight to its own RET when `[0x8A5]==0`" because its own `[0x8A5]` test sits at `2447`, close to the function's own end (`2480`) — but that test only gates the LAST ~50 bytes (drawing two win-tally digit sprites); everything from the function's own start through `2447` (masking both players' own portrait-frame fields, redrawing both portraits, drawing an outline and the character's own name) runs UNCONDITIONALLY regardless of the gate. When a citation says a gated check controls "the whole function," verify that by reading from the function's own ENTRY forward to the gate, not just the gate itself backward to nothing.
- **A chained `input_sequence`'s own release order decides the FINAL committed value of a "hold two keys together" test, not just an intermediate one.** Releasing two held keys a few ms apart, the natural shape of a single chained `input_sequence` call (`{key:A,pressed:false,delay_ms:X},{key:B,pressed:false,delay_ms:Y}`), leaves a brief window where only ONE is still down. A level-based poll that re-evaluates every tick (the handicap question's own LEFT/RIGHT toggle, `docs/engine.md` §9bn) re-evaluates during exactly that window too, so whatever the LAST-released key alone would produce can silently overwrite the "both held" result right before a downstream commit reads it (`docs/engine.md` §9bn hit this TWICE testing the same mechanism: once between a press-together read and a same-call release, once again releasing the two keys in the wrong order on a SEPARATE call meant to fix the first). To test "both held," read the value WHILE both are still genuinely down (a separate `input_sequence` call for the press, `mem_read` in between, release sent only afterward) rather than trusting a value read after any release. To then commit a specific outcome, release the key whose OWN bit should NOT win first, re-read the toggle to confirm it still shows the intended value, and only then send the confirm/fire press -- releasing both together (or in the wrong order) risks a single-key window flipping the result one more time.
- **A `CS:`-segment-override operand with an offset `>=0x93C0` is a `DS:`-relative address in disguise, not automatically a dead constant.** This binary's own `CS` segment (`0x1000`) and `DS` segment (`0x193C`) are exactly `0x93C0` paragraphs apart, so `CS:[X]` and `DS:[X-0x93C0]` are the SAME physical byte for any `X>=0x93C0` (already established once for `CS:[0x9C62]`≡`DS:[0x8A2]`, §9bf/§9bg -- then INDEPENDENTLY REDISCOVERED the hard way for `CS:[0x93C2]`≡`DS:[0x2]` and `CS:[0xA329]`≡`DS:[0x0F69]`, both already-CLOSED `UNKNOWN` items reopened and reversed, `docs/engine.md` §9bn/§9ar). A `search_byte_patterns` sweep for the literal `CS:[X]` byte encoding only proves nothing ELSE reads that SAME ENCODING -- it says nothing about whether the SAME PHYSICAL BYTE has writers under a completely different (`DS:`-relative, no override) encoding, which is a different search entirely. A static `read_memory` of `0` at the `CS:`-relative address cannot distinguish "genuinely dead, never written" from "aliases a byte that's simply `0` in the unrun static image" -- both look identical without a live capture or a check for the alias's own real writers. A Ghidra xref that SEEMS to point somewhere unexpected (e.g. one instruction's own operand cross-referenced to a DIFFERENT address than the one being investigated) may be Ghidra correctly resolving the SAME linear byte through the alias, not a stale/wrong xref to be dismissed -- verify the linear address match with segment arithmetic before calling an inconvenient xref "stale." Before closing any `UNKNOWN_*` item as "constant, no writer" from a `CS:`-relative read, compute whether its own offset is `>=0x93C0` (or, more generally, whether `CS_offset - (DS_segment - CS_segment)*16` lands on an address with independently-known writers) and check THAT address's own writers too.
