# Track layout: `.MAP`, `.COL`, `.DIR`, `.CT`, `STRT_POS.BIN`, `CHEATS.BIN`

Evidence tags as in `CLAUDE.md`; addresses are Ghidra program `MICROU.EXE` (`1000:`-based, `DS = 193C`). Established by the research workflow's `file-io-map` and `data-and-tables` agents from the consumer code, ported to `src/formats/track.js` and checked by rendering all 29 tracks (`tools/out/TRACK_col_masks.png`).

## World model `[STATIC]` from the consumers

- The race world is **3072×3072 units**: **32×32 tiles of 96 units**, each tile **12×12 cells of 8 units**. `TestColMaskBitAtWorldXY 1000:589c`: `col = x/96`, `row = y/96`, `subx = (x%96)>>3`, `suby = (y%96)>>3`.
- **Race loading, corrected.** `1000:37fc` (previously documented here as `SetupRaceLoadAllRoundFiles` with a `BRK→LEV→STRT_POS→CHEATS→MAP→CT→COL→DIR→BITSFILE→VH0→PR→PAL` order) is **not a function**: it is 255 bytes of `0x90` (NOP) filler, confirmed in the raw `MICROU.EXE` file bytes as well as in Ghidra, sitting between a `RET` and real code — renamed `NoppedOut255bStub` with the evidence in its plate comment. **Correction (`docs/engine.md` §2/§9, supersedes the paragraph that used to follow): the NOP slide is not a dead branch.** `RunRaceMainLoop`'s function entry is `1000:3039`, not `3043` — `3043` is merely the address of the `CALL 37fc` instruction inside it. The 255-byte NOP run falls straight through into real code, `LoadRaceStartPosCheatsMapAndBanks` (`1000:38fb`), which ends `CLC/RET` or `STC/RET`; the `JNC` at `1000:3046` is therefore the **live** race-load success test, not dead code (confirmed: every loader step inside `38fb` branches to its own failure exit on `CF`). What follows is otherwise as previously recorded: `ChdirGameSetAndPatchRoundFilenames 1000:3b50` chdirs `GAME1`, patches the round/race ASCII digits into the resident filename table at `DS:11A0–1230`, then itself loads **`ROUNDnnB.BRK` and `ROUNDnBR.LEV` first** (`3b83`/`3bab`, buffers below), before setting up the per-round tile-dispatch pointer `DS:28BD` from the table at `DS:26D7`. Its caller `LoadRaceStartPosCheatsMapAndBanks 1000:38fb` then loads `STRT_POS.BIN` → `DS:1EAB` (`3cc7–3ce7`), `CHEATS.BIN` → `DS:1BDB` (`3ce9–3d09`), `ROUNDnm.MAP` → `DS:2963` (`3d0b–3d2b`, plane-2 max-scan immediately after; this whole load path — `STRT_POS`/`CHEATS`/`MAP`/car-init — is `InitRaceCarsFromTables 1000:3c09–458a`, a verified function boundary ending `CALL 2d00; RET`), then calls `1000:458b` (`ROUNDn.COL` → `DS:3163`, `ROUNDn.DIR` → `DS:35E3`), then — confirmed by direct disassembly of the straight-line call sequence at `1000:3942–3955`, no branch between them — `LoadBitsFilePh0 1000:482F`, **then** `LoadRoundVh0AndSplit 1000:4611`, **then** `LoadRoundPrFilesThenCopyPr0Header 1000:45E5` (so `BITSFILE.PH0` loads before `.VH0`, and `.VH0` before the `.PR0–2` series — the reverse of what the address order 45E5 < 4611 might suggest). This order matters: it is why round 8's `.VH0`-bank-2-to-`DS:5EE3` copy (`docs/track-graphics.md`) durably overwrites `BITSFILE.PH0`'s own bytes at that offset for the rest of the race, rather than being clobbered by a later PH0 reload. `.PAL` (`1000:4765`) and `.CT` (`1000:446a`) load sites were located by filename xref but not retraced. Filenames are built by patching ASCII digits into the same `DS:11A0–1230` table (`ChdirGameSetAndPatchRoundFilenames`). Every read is whole and verbatim — **`[PROVEN]` live for round 2 race 1** (the graphics/collision path); the file-loading call graph above is `[STATIC]`. Full engine-facing detail (per-iteration order, the overlay bit-15 pass being hard-coded to rounds 2/3 with no table, race setup and race-over paths) is in `docs/engine.md` §2.

## `.MAP` (2048 B) `[PROVEN]` by render

- Bytes 0–1023: the **32×32 tile map**, `[row*32 + col]`. Bits 0–5 = tile index into the per-round tables (`AND 0x3F` at `1000:58c8`), bits 6–7 = a 2-bit attribute (`DI = byte>>6` at `1000:58cd`, stored to a car's `[BX+12DE]`). `UNKNOWN_map_attr_bits` is now partial, not fully open: two consumers of `[BX+12DE]` are traced (`1000:544e`/`6250`, `1000:5478`/(the mirrored site near `6264`)) — attribute **bit 1** (`TEST DX,2`) gates whether the `.DIR`-driven heading remap (`DS:191B`, see `.DIR` below) is applied at all, and attribute **bit 0** (`TEST DX,1`) flips the final looked-up heading 180° (`XOR AX,0x80`). What bit 1 = 0 means physically (the remap is skipped, not zeroed) and why round 8 sets this bit along the course are still open.
- Bytes 1024–2047: a parallel 32×32 byte plane (`MAP[1024+idx]`, read at `1000:58d8` inside `TestColMaskBitAtWorldXY`; max-scanned at `1000:3d32–3d4b` into `[2652]`/`[2654]=max>>1`). **The lap-progress hypothesis is `[STATIC]`, now with strong corroboration**: disassembly shows this byte is the value that ends up in a car's `[BX+12E3]`/`[BX+12E1]` fields (via `TestColMaskBitAtWorldXY`'s output, threaded through at `1000:55d5–55db` and `1000:7121–7126`) — **but only when the byte is nonzero** (`561d`/`579a`/`5807`, `[PROVEN]` live, `docs/engine.md` §9ah: a 0 cell, i.e. anything off the numbered centre line, leaves both fields alone and the lap logic skips that tick; the respawn at `7121–712a` is the one unconditional write) — the same fields used both by the lap/checkpoint rule (`1000:5f25`, compared against `[2654]`; not a wrong-way check) and, directly as a byte offset, to index the `.BRK` brake-point stream (`1000:5495`, see below). Measured across all 26 races (a script over the real files, not a live trace): `(round's plane-2 max byte) >> 1` is always safely below that race's `.BRK` file size — but this halved comparison is NOT the one that matters for `.BRK`'s own indexing safety, which uses the RAW value. **`UNKNOWN_589c_progress_transform` resolved (`docs/engine.md` §9ad, re-disassembling `1000:58c0–5920` in full): there is no transform — the function returns the raw plane-2 byte completely unmodified** (this paragraph's own earlier "not fully unwound" claim was stale, contradicted by this project's own "Open items" section below, which already had the correct closed status). Round 3's own plane-2 bytes genuinely saturate at 255 in real, reachable course data (confirmed by a full sub-cell flood fill from each race's own start, `docs/engine.md` §9ad — not a dead corner, unlike `UNKNOWN_tile_index_overflow`'s own `.COL`/`.DIR` cases) — and since `.BRK` is indexed by this RAW value directly (`1000:5495`), not the halved one, round 3's own real `.BRK` files (134–156 B) genuinely get read past their own content when a car's progress reaches 255. Safe (the real buffer is a fixed, never-cleared 512 B allocation, `1000:3b92`, the same shape as `.COL`/`.DIR`'s own buffers) but not the file's own data — see `docs/engine.md` §9ad for the full account and the port's own opt-in replication of it.
- Quirks: `ROUND82.MAP` references tile 58 while `ROUND8.COL` holds 49 tiles; `ROUND92.MAP` references tile 60 of 59. The collision read then lands past the loaded bytes inside the 0x480-byte `colFileBuf`. **`UNKNOWN_tile_index_overflow` resolved (`docs/engine.md` §9ac):** both cells are structurally unreachable (a full sub-cell flood fill from each race's own start position never touches even their tile boundary) — the port's "open, no special terrain" fallback is safe because the tile is never actually queried by a driving car. A third, previously undocumented case is real and reachable: `ROUND5.DIR` itself ends 18 bytes into meta-tile 56's own 36-byte record (races 1 and 3), and that tile is fully open and sits on the real racing line — the port now uses the file's genuinely-present 18 bytes instead of discarding them along with the missing 18, per `docs/engine.md` §9ac's full account.
- The earlier "32×32 words" hypothesis was wrong because the file is two byte planes, not one word plane.

## `.COL` (18 B per tile) `[PROVEN]` by render

12×12 one-bit collision mask per tile, MSB first, row-major: `SI = tile*18 + (suby*12+subx)/8`, `mask = 0x80 >> ((suby*12+subx) % 8)`, carry set = solid (`1000:589c–5920`). Tile count = size/18 (rounds: 62, 60, 64, 64, 57, 56, 54, 49, 59). Rendering `MAP × COL` for all 29 tracks gives coherent courses: closed circuits with solid surroundings for round 8, obstacle fields on the desk/bathtub, table rims on the pool table.

## `.DIR` (36 B per tile) `[STATIC]` for the bit-field model; `[PROVEN]` by render for the flow field itself — `UNKNOWN_dir_values` resolved

`LookupDirByteForCar 1000:585b`: `SI = tile*36 + (subx>>1) + 3*(suby & ~1)`, i.e. 6×6 bytes per tile, one per 2×2-cell block, stored 6 per row; the byte goes to the car record (`[BX+12DA]`, previous value shifted to `[BX+12DC]`), called from `UpdateCarTileCollisionSfx6or4` (`1000:5532`) immediately after `TestColMaskBitAtWorldXY`. It is genuinely a **direction/flow field the AI follows**, but the byte packs two unrelated fields rather than one direction value:

- **High nibble (bits 7–4, `AX>>4`) — a terrain roughness/ramp grade, 0–15.** Consumed by the same class-based terrain-immunity checks documented in `docs/sound.md` §3b for sfx id 6: TANKS (class 7) are immune for grade `1–7` (`1000:55e5–55fd`), TURBO WHEELS/FOUR BY FOUR (classes 4/5) for grade `≥5` (`1000:5600–561a`); grade `0` and, for tanks, `8–15` are never immune. Bit 4 alone (`0x10`, the grade's LSB) is also tested standalone as a **ramp flag**: `1000:687c` (`LaunchCarJumpFromRampSfx1`) tests it on the *previous* tick's byte (`[BX+12DC]`) to launch a jump; `1000:6ac2` tests it on the *current* byte (`[BX+12DA]`) to set `[BX+1388]=1` (an airborne/jump-state flag). That two ramp-adjacent grades (an even/odd pair) differ only in the ramp bit, and TANKS' immunity band starts exactly at grade 1, fits a scheme where each terrain type has a "smooth" and "has a ramp" variant packed into one 4-bit value. **Correction (`docs/engine.md` §5/§9):** the terrain-**dispatch** index computed in `UpdateCarCheckpointsAndSurfaceSfx 5e4e` is not uniformly "the high nibble" — it is `[12DA] >> 5` (bits 7–5, 0–7) for rounds 1, 2, 3, 6, and `>> 4` (bits 7–4, 0–15) only for rounds 4, 5, 7, 8, 9; and for rounds 4/5 the dispatch values 5–14 are not a roughness grade at all but **stepped height levels** (`level = idx − 4`, wall probes on a level jump > 1). All 9 rounds' dispatch rows are listed verbatim, per handler, in `docs/engine.md` §5.
- **Low nibble (bits 3–0, or bits 2–0 for POWERBOATS — `AND AX, 0xF` vs `AND AX, 0x7` at `1000:544b`/`5448`, mirrored at `6249`/`6246`) — a per-sub-block recommended-direction index feeding a two-stage heading lookup**, confirmed end to end (one loose thread: round 2 — the one POWERBOATS round — has low-nibble values `8–15` in its actual `.DIR` file despite the game masking that bit away for class 2, i.e. the authoring tool wrote bits the engine provably never reads back for that round; read as a toolchain artefact rather than a sign the class check is mis-read, but not confirmed either way):
  1. `bucket = ([BX+12E0] >> 5) & 3` (0–3) selects one of 4 rows of a **16-column remap table at `DS:191B`** (4×16 = 64 bytes, dumped and inspected: every entry is itself a nibble 0–15).
  2. `SI = 0x191B + bucket*16 + dir_low_nibble` → `LODSB` gives the remapped direction (`1000:5454–5465`).
  3. That value indexes a **16-entry, one-word-per-entry table at `DS:18FB`**: `word = TABLE[remapped*2]`. Dumped and checked exhaustively — **the 16 words are exactly the 16 multiples of 16 from 0 to 240, each appearing once** — i.e. a genuine 16-point compass in the same 0–255 byte-angle convention used elsewhere in this codebase (`docs/sound.md`'s engine-bend math), just stored in a track-author-chosen (non-monotonic) order rather than compass order. This is the strongest evidence for the whole model: a wrong bit-split would not reproduce "all 16 compass points, no duplicates, no gaps."
  4. MAP attribute bit 0 (`[BX+12DE]`) XORs `0x80` onto the result (mirror 180°); the value is then compared against the car's current heading (`[BX+1278]`) to drive the AI steering-intent bits in `[BX+137B]` (`docs/track-layout.md` `.BRK` section above shares this same routine).

  **`UNKNOWN_dir_bucket_source` is now closed (`docs/engine.md` §3/§9), and the earlier caveat below was wrong about the writer.** `1000:5de6` is *not* inside a projectile-hit routine — `FUN_1000_5be7` (`5be7–5e4d`) is the **per-car integrate/wall-bounce/commit routine**, called for all 4 cars every physics step (`5001–5016`; the `[PROVEN]`-tagged Ghidra comment that used to sit on this address is stale). Every time a car's position is committed, `5de6` writes `[BX+12E0] = LEV[[BX+12CC] & 0x3F]` — the `.LEV` byte of that car's own **current** meta-tile, unconditionally, not just after a projectile hit. Bits 6–5 of that byte are exactly the `bucket` this section reads at `5454`, so **the DIR remap row is the current tile's `.LEV` field**, genuinely varying car-to-car and tile-to-tile as the flow field crosses `.LEV` boundaries — it is not stuck at row 0 for ordinary play.

Round 8's file is 2300 bytes = 63 tiles + 32 spare bytes (not 2× COL). A per-round nibble histogram (script over the real files, not live) shows every round using a wide spread of both nibbles except round 8 (high nibble only ever 0/1/2 — round 8 is CHOPPERS, i.e. it may need little or no terrain-roughness signalling) and round 9 (both nibbles capped at 7 — round 9 is RUFFTRUX; consistent with, but not proof of, class-specific track authoring).

**Rendered and looked at** (`npm run` has no entry for this; `node tools/render-dir.mjs` writes `tools/out/DIR_ROUNDn_{grade,heading}.png` for all 9 rounds): the *direction* image (bucket 0, i.e. what an ordinary car actually samples) is not noise — it draws a single coherent, closed path tracing the track's own racing line in round 1's oval and round 5's winding room-with-obstacle layout, with distinct accent colours clustering at the turns; round 3's (Formula One) is busier but still structured, not random. This is the strongest evidence for the model: a wrong bit-split would render as static, not as a path that visibly follows the track.

## `.CT` (72 B per tile) `[PROVEN]` by the live diff — `UNKNOWN_ct_tile_pixel_layout` resolved

`InitRaceCarsFromTables 1000:448c–4575` reads the file into the work segment and, for every map cell, copies the tile's 72 bytes as **6 rows × 12 bytes** into two arenas (`4B78:0000`, `5478:0000`, `0x9000` each: row stride `0x180` = 32 tiles × 12 B, tile-row stride `0x780`). 72 = 4 × 18 explains the measured `CT = 4 × COL`. **`UNKNOWN_ct_tile_pixel_layout` resolved: neither hypothesis this section used to pose (12×6 8-bpp pixels, or two 4-bit nibble-cells per byte) is right — `.CT` is not pixel data at all.** Each 72-byte record is **6×6 little-endian 16-bit tile-index words** (bits 0–14 = an index into the round's own `.PR` 256-byte tile bank, `word = 4 × 12-byte .COL record size` no longer needing an explanation once the unit is a word, not a byte): the "striped" look of a naive 12×6 8-bpp render was a real symptom of treating index words as raw palette bytes, not evidence the byte-count was wrong. Already correctly resolved and implemented elsewhere in this project (`docs/track-graphics.md`'s "The world map" section, `src/formats/race.js`'s `buildWordMap`, real callers `src/play.js`/`src/frontend/flow.js`) — this section's own text was simply never updated to match, the same "one doc/section says resolved, a sibling doesn't" pattern this project has hit before (`docs/track-layout.md`'s own `.MAP` section once had the identical problem with `UNKNOWN_589c_progress_transform`, `docs/engine.md` §9ad). Re-verified independently this session by a fresh live disassembly of the post-processing pass (`1000:3994–39e4`) and its read site (`1000:9203–9237`): the pass is **word-sized throughout** (`LODSW`/`STOSW`/`OR AX,0x8000`, not byte instructions), applied to BOTH arenas identically, and is **hard-coded per round, not a value-range table** — round 2 ORs bit 15 into words `0x40..0x13C`, round 3 into `0x01..0x51`, every other round gets no overlay pass at all (`byte [DS:042E]=='1'`, the game-set name, gates the whole pass; `[DS:28BF]`, the round number, picks the range). Bit 15 itself is not stored in the `.CT` file — it's an engine-added overlay/draw-order flag OR'd into the assembled word map at race-setup time, consumed as a boolean "redraw this tile's `idx+12` variant after cars" marker (`docs/track-graphics.md`'s own "Overlay tiles" note). `npm run live`'s own pixel-exact check happens to render round 2 race 1 with overlay-flagged tiles present, but with no car ever positioned under one (and no car sprite drawn in that check at all) — so it independently confirms every overlay tile's `+12` variant equals its base graphic absent a car, but does NOT exercise the cars-under-an-overlay z-order case (`UNKNOWN_overlay_tile_191`, docs/track-graphics.md, remains its own separate, still-open question).

## `ROUNDnBR.LEV` (one byte per meta-tile, 49–64 B) `[PROVEN]`, structure and bit-field model

One byte per meta-tile — file size equals the round's tile count (`.COL`/`.CT`) exactly for 8 of 9 rounds; round 2 is 63 B for 60 tiles. **`UNKNOWN_lev_round2_size` resolved 2026-09-23 (closes as a harmless authoring artifact, not further resolvable):** the load site (`1000:3bba–3bc7`) reads a **fixed 128-byte (`CX=0x80`) buffer**, not a tile-count-derived length — confirmed by disassembly (`MOV DX,0x1b5b; MOV CX,0x80; AH=3Fh; INT 21h`) and by the next loaded structure's own base address (`CHEATS.BIN` → `DS:1BDB`, exactly `0x1B5B+0x80`); the transfer-count `AX` the DOS read returns is never checked afterward, so the loader is fully length-agnostic and simply uses whatever the file happens to hold. Round 2's real 63 real-file bytes (offsets 60–62 = `0xA0, 0xC0, 0x22`, values that recur throughout the file's own first 60 bytes, not zero padding or a repeat of the start) decode to ordinary, well-formed fields under the bit model below — they just happen to sit past both traced consumers' own reach: a fresh scan of all four `ROUND2{1,2,3,4}.MAP` files' tile-index bytes (`AND 0x3F`) finds a maximum index of 59, so meta-tiles 60/61/62 are never queried by either `.LEV` consumer in any round-2 race. A cross-round check found no length invariant these 3 bytes could even be "wrong" against: 7 of 9 rounds have `.LEV` size == tile count exactly, rounds 8/9 have real `.MAP` references exceeding both (the already-resolved, unreachable `UNKNOWN_tile_index_overflow` cases) — round 2 is the only round with LEV headroom rather than shortfall, and there is no rule anywhere in the loader that a correct file would need to satisfy in either direction. Loaded whole into `DS:1B5B` (pointer `DS:28B9`) by `ChdirGameSetAndPatchRoundFilenames` (`1000:3bab–3bcb`). Two consumers, both confirmed by direct disassembly:

- **`1000:5de6`** `[STATIC]`. **Corrected (`docs/engine.md` §3/§9): not the shooting projectile's tile, and bit 7 is not a projectile line-of-sight flag.** The containing function `FUN_1000_5be7` is the per-car integrate/wall-bounce/commit routine, run for **every** car on **every** physics step (`5001–5016`), not a projectile-hit routine. `AL = LEV[[BX+12CC] & 0x3F]` reads **that car's own current meta-tile** (`[BX+12CC]`, set by `TestColMaskBitAtWorldXY`'s caller, not a projectile record) and stores it to `[BX+12E0]` — which is also the `.DIR` remap bucket, see above. **Bit 7 set skips only the safe-respawn-point update** (`[BX+12F1]/[12F3] ← position`) for that tick — "this tile is not a safe place to remember as a respawn point" — not hit detection: the projectile-hit test (`CheckProjectileHitsOnCarSfx1 1000:79fd`) is called immediately afterward regardless of this bit, from the same routine, for TANKS cars or when `[2919]` is set.
- **`1000:70c8`**, inside the car respawn routine — now bounded: **state 7's handler, `6feb–73e6`** (`docs/engine.md` §4). `CL = LEV[SI]` where `SI` is the meta-tile the just-grid-snapped (96 px cell) respawn point falls in. The byte packs two more fields, both confirmed against their consumer tables:
  - **bits 4–2** (`AND 0x1C`, used pre-multiplied by 4) index one of **8 `{dx, dy}` int16 nudge vectors** at `DS:1FCB`, added to the snapped position. Dumped: `(0,0) (36,−36) (−36,36) (−36,0) (36,36) (−36,−36) (36,0) (0,−36)` — an 8-point compass rose using only `{−36, 0, +36}` components, i.e. this nudges the spawn point off dead-centre so cars don't stack.
  - **bits 6–5** (`>>5 & 3`) select a base heading — `0x40 / 0x80 / 0x60 / 0xA0` (table at `1000:7181–719f`) — **corrected: XORed by the `.MAP` attribute bits, not the `.DIR` byte.** Disassembly at `71a2–71b1` tests `DI` (the `.MAP` attribute from `TestColMaskBitAtWorldXY`, `[BX+12DE]`), applying `XOR 0x80` once for attribute bit 1 and again for bit 0, then stores into the car's heading field `[BX+1278]`.
  - **bits 1–0**: not exercised by either traced consumer; purpose open (`UNKNOWN_lev_low_bits`).

Both consumers derive the meta-tile index the same way as `.COL`/`.CT`/`.DIR` (`TestColMaskBitAtWorldXY`), so `.LEV` is squarely part of that per-tile family: **per-meta-tile placement/orientation and safe-respawn data**, not "level" in the sense of a difficulty or height table, and not a projectile line-of-sight table.

## `ROUNDnmB.BRK` (29–183 B) `[STATIC]`, structure and record semantics both resolved by disassembly

A **variable-length stream of AI brake/speed-limit records**, one file per race (not per round — file size scales with the race's own track complexity, not tile count). Loaded whole into `DS:195B` (pointer `DS:28BB`, 0 if the open fails — round 9 ships no `.BRK` files at all and gets the null pointer) by `ChdirGameSetAndPatchRoundFilenames` (`1000:3b83–3ba8`).

**`UNKNOWN_brk_nibble_reuse` closed 2026-09-23** (full re-disassembly of `1000:5495–5531`, `RunDroneSteeringAi`, `[PROVEN]` by disassembly, no second consumer needed): the dispatch is not "0/3/4/15 all reach the identical `54AF` branch". High nibble `0` takes a **direct** `JZ 54B7` (`54A3–54A5`) that *bypasses* `54AF` entirely — its low nibble is never read and it never brakes. High nibbles `3/4/15` (and hypothetical `5–14`) fall through the explicit `0`/`1`/`2` compares to `54AF`, which tests the steering-intent flags `[BX+137B]&0xC0` set two instructions earlier by the heading-vs-target-heading block (`547B–5490`: bit `0x80` for a negative heading error, `0x40` for `diff>=3`, neither for `diff` in `[0,3)`, i.e. "already near-enough on heading"). If either bit is set (drone actively correcting) it falls into `54E0` — **the same handler as an explicit type-1 record, using this byte's own low nibble** as the threshold scale. If neither bit is set it falls to `54B7`, identical to type `0`. **So `0` vs `4`/`15` are genuinely distinguishable in play: `0` is an unconditional "just advance" waypoint, `4`/`15` are a corner-brake check that only arms while the drone is already mid-correction** — that's exactly why the level-design tool bothers writing 283 `4`s and 23 `15`s. The narrower claim survives unchanged: `3`, `4` and `15` **are** mutually indistinguishable from each other (all three reach `54AF` identically; the 3 stray `3`s are presumably typos of `0`). Full-coverage confirmation that nothing else in the program touches this data: `search_instructions` (operand substring, no bracket, whole-program scope, 13420 instructions scanned) for `28bb` and for `195b` each return exactly 2 hits — the known loader write (`1000:3ba8`) + AI read (`1000:5495`) for the pointer, and the loader's two own immediate loads of the buffer literal — nothing else, anywhere. `get_xrefs_to` alone under-reports (misses the `5495` read entirely, a live instance of this project's own documented `get_xrefs_to`-incompleteness pitfall), so the `search_instructions` sweep is the authoritative one. A `search_byte_patterns` sweep for the raw operand bytes (`?? BB 28`, `?? 5B 19`, coverage = 83662 bytes = the whole file's defined content, the rest of the declared 947744 B being uninitialized/never-loaded segments) turned up only two extra hits, both verified false positives (`1000:122a`, `1000:9311`: unrelated `MOV BX,0x28` instructions). A third, index-based check (`search_instructions` on `12e3`, the track-progress field used as the `.BRK` offset) finds 19 hits total; only `1000:5499` combines it with the `.BRK` base — every other hit is checkpoint/wrong-way/respawn/HUD code with no `.BRK` involvement. `secondConsumerFound = false`, definitively.

**`UNKNOWN_brk_record_types` closed 2026-09-23** — types 1 and 2 are not symmetric "check a limit, maybe brake" variants; they are asymmetric and address different fields:

```
SI = DS:28BB + [BX+12E3]        ; 12E3 = this car's current track-progress value (see .MAP plane 2 above)
AL = BRK[SI]; AH = full byte (549D–549E); hi_nibble = AL >> 4 (54A0)
  0                 -> 54B7: unconditionally OR 0x20 into [137B]; copy [BX+129E] into [BX+129C] (advance target speed). Low nibble never read.
  3, 4, 15 (5-14 unused) -> 54AF: if [137B]&0xC0 (drone mid-heading-correction) goto the type-1 handler below using THIS byte's own low nibble; else behave exactly like 0.
  1 (54E0-5527)     -> threshold = (low_nibble<<7) + 0x380 [896 + 128n; n=0->896, n=8->1920, n=15(0xF)->2816],
                        +0x50 if tournament index [28C1]==0x17(23); if class [28BF]==7 (TANKS): -0xD0 always, further -0x20 if [28C1]>=0x13(19).
                        CMP [BX+127A] (CURRENT speed) vs threshold: JG -> OR 0x10 (brake-intent); else OR 0x20 (cruise-intent).
                        BOTH branches still copy [BX+129E] into [BX+129C] (target speed always advances regardless of the brake test).
  2 (54C6-54DF)     -> threshold = (low_nibble<<6) + 0x600 [1536 + 64n; n=0->1536, n=8->2048, n=15->2496]. Unconditionally OR 0x20 (never sets the brake bit 0x10).
                        CMP [BX+129C] (TARGET speed, not current) vs threshold: JG 5528 (skip) -> if target already exceeds threshold, LEAVE IT; else MOV [BX+129C]=threshold (raise it up).
                        Net effect: [BX+129C] := max([BX+129C], threshold) — a FLOOR, never a cap; type 2 can never brake.
```

Read plainly: **type 1 is the only record type that can set the brake bit**, and it does so reactively, off the car's *current* instantaneous speed (`[BX+127A]`) — a hard corner/section speed limit ("you're going too fast right now, brake"), tuned per tournament race (`[28C1]`) and per vehicle class (TANKS gets a flat, large downward offset matching its slower absolute speed range). **Type 2 never brakes**; it only ever raises the car's forward-looking *target* speed (`[BX+129C]`) up to a floor, never lowers it — a "don't let your commanded pace sag here" / resume-speed marker, plausibly placed coming out of a corner or slow section so a drone doesn't stay overly conservative. The two are not two scaled variants of one concept: one is a reactive brake check on current speed, the other is a one-directional floor on the AI's own target speed that structurally cannot brake. `[STATIC]`: re-disassembly (`1000:5429–5531` in full) + cross-file byte tabulation (`{0: 957, 1: 1313, 2: 21, 3: 3, 4: 283, 15: 23}`, never `5`–`14`); not independently confirmed against a live DOSBox trace.

## `SETTINGS.DAT` (32 B) `[STATIC]`, layout from `RunOptionsScreenWithSettingsDat 1000:2770`; decoded, readout view added

The live traces' ESC-quit and RETURN-to-play wrote nothing — the file was byte-identical before and after every session (`[PROVEN]`). **`UNKNOWN_settings_key_slots` is closed (`docs/engine.md` §6/§9): the 5 slots are LEFT, RIGHT, ACCELERATE, BRAKE, SELECT (fire), in that order** — `RunRedefineKeysScreen 1000:92f0` labels them from the string block at `DS:AE4B` and stores the chosen scancodes back to `DS:106C`/`1074` in that order (`93af–93ba`); `KeyboardIsr 1000:2efd` maps scancode-table slot *i* to bit `0x8000 >> i` of `[107C]` (KEYS1 → the high byte `[107D]`, bits `0x80..0x08`; KEYS2 → the low byte `[107C]`, same bits), and `1000:4aee` reads those bits directly as `0x80` left, `0x40` right, `0x20` accelerate, `0x10` brake, `0x08` fire.
